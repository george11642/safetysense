Attachment 5 of 5 · Security & privacy

Listens only when asked. Keeps nothing unless something's wrong.

SafetySense handles some of the most sensitive data a student has: where they are, what's happening around them, and possibly evidence of an assault. This document lists every piece of data we hold, how it's protected, the threats we designed for, and the limits we haven't solved yet.

01Design principles

On-device first

Sound classification, speech recognition and the AI second opinion all run on the iPhone. None of them has a server path.

Nothing saved by default

While guarding, audio exists only in a 30-second RAM buffer that's constantly overwritten. Nothing is written to disk.

Server sees the minimum

The server gets a heartbeat and contact details. Evidence reaches it only as ciphertext, and it never holds the key.

No trackers

No third-party iOS SDKs at all: no analytics, ads or crash reporters. Data is never sold or shared for marketing.

03How the protections work

  • RAM-only bufferA fixed-size PCMRingBuffer of mono samples is overwritten in place. When the ladder reaches Alert, those 30 seconds and the live audio after them are encrypted the moment they're captured. Below Alert, nothing is persisted.
  • Evidence vaultCryptoKit AES-GCM with a 256-bit key generated on the device (kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly). Each chunk's SHA-256 is shown in the Vault and stored with the upload, so tampering is detectable. A swapped or reordered chunk fails to decrypt because the alert ID and sequence number are bound in. Chunks upload while recording, so evidence survives a smashed phone. The Vault opens only with Face ID or the passcode, and sharing it with an advocate or police is always the user's choice.
  • Server lockdownEvery table has RLS enabled with no policies, and anon and authenticated have no grants. Only the edge function's service role touches data, so the public key alone reads nothing. Secrets live in Supabase Vault and are read through a SECURITY DEFINER function that only the service role can run. The cron job reads its secret from Vault at run time, so it never appears in the job table.
  • AuthenticationDevice routes need the device ID and secret, checked against a stored hash in constant time. Share routes are scoped to one alert's token. Twilio callbacks must carry a valid X-Twilio-Signature (HMAC-SHA1), and the watchdog requires a secret header. Admin setup is hash-gated and switched off.
  • Abuse limitsAt most 6 live alerts per device per hour, 5 contacts, and US numbers only. One live alert per session, so repeat requests reuse it. A practice drill runs as a dry run and is labelled TEST, and dry runs never call Twilio.
  • Duress PINDuress is checked before the real PIN, so it can never count as a valid cancel. The phone shows "cancelled" and the API answers {status:"cancelled"}, but the server silently escalates and keeps the alert live for contacts. alert/status hides the dispatch from the phone, so someone looking over the user's shoulder sees nothing unusual. Noonlight's API has no duress flag, so dispatch is given a relay number, not the user's phone, and the server decides each call when it arrives. Once the server has the duress PIN, the relay never connects a call to the phone. It tells the caller the person may be coerced, not to call or text them, and to send police to the shared location. This holds whichever came first, the PIN or the dispatch, and a failed lookup counts as duress. It is tested with simulated calls and the Noonlight sandbox, not a real dispatcher call (see Limitations). A wrong PIN never cancels.

05Legal and compliance posture

  • Recording consent (New Mexico). NMSA 1978 § 30-12-1(C) prohibits intercepting telegraph or telephone communications "without the consent of a sender or intended recipient," which makes New Mexico a one-party-consent state for calls. The statute's text addresses telegraph and telephone communications, and how it applies to in-person audio captured by a phone is less clear. § 30-12-11 also gives a civil remedy for intercepted wire or oral communications. SafetySense lowers the risk by design: it records nothing until an Alert, the user is present at the conversation, and evidence is never shared automatically. (Statute text checked Nov 4, 2026; this is not legal advice.) Legal review before launch
  • HIPAA: doesn't apply. SafetySense isn't a covered entity or business associate. Medical notes are entered by the user, stay on the device, and are still treated as sensitive.
  • FERPA: doesn't apply. We don't receive education records from UNM or CNM. If a campus integration ever shares institutional data, we'd work under the institution's data-sharing agreement.
  • Title IX and Clery: SafetySense never reports to a school or the police on its own. Reporting options are offered, never required, so the student stays in control. Any campus partnership would be reviewed with the Title IX offices for responsible-employee implications.
  • Breach response: we'd follow New Mexico's Data Breach Notification Act (NMSA 1978 §§ 57-12C-1 to -12): notify affected users within 45 calendar days of discovery, and the Attorney General too if more than 1,000 New Mexicans are affected.
  • App Store: privacy nutrition label "Data Linked to You" (contact info, location), no tracking, a purpose string for each permission, and permissions requested only when needed. The audience is 18 and over.
  • Emergency services: SafetySense supplements 911 and never replaces it. The demo uses only the Noonlight sandbox or a clearly labelled simulated dispatch, never live 911.

06Limitations we're stating plainly

  • Duress relay. Voice is tested only with signed, simulated webhooks and the Noonlight sandbox. No real dispatcher call has happened. Noonlight's sandbox has really texted the relay: those texts are logged without their content and never forwarded, so a dispatcher's text never reaches the user on any alert. The prototype has one relay number, and production needs one per active alarm. Noonlight has not confirmed that a relay number is allowed, and nothing guarantees a dispatcher follows the spoken message. A call that lands before the server has the duress PIN, for example while the phone is offline, can ring the phone. A forward taken back after duress can leave a missed-call notice. A contact can still dial the user directly.
  • Duress paths still open. The alert screen offers "Share link", and that link opened on the held phone shows the escalation and a "Do not call or text" banner. A duress PIN notifies contacts and a real cancel doesn't, so someone who is a listed contact would be alerted. The Vault hides a duress recording only in memory, so after a relaunch or 30 minutes it can list clips timed after the PIN. Silent triggers (safe word, Action Button) forward a dispatcher's call to the phone like any other alert.
  • Phone numbers in server logs. The relay's lookups put phone numbers in request URLs, and Supabase's gateway logs keep those URLs. That includes the user's number and callers' numbers. The planned fix moves the lookups into a POST body. Rows already logged stay until Supabase ages them out.
  • Evidence key recovery. The key is bound to the device, so if the phone is destroyed the server-side ciphertext can't be read. Planned fix: an optional recovery key the user stores themselves, or an escrow shared with an advocate the user picks.
  • Server-side deletion during a live alert. "Delete everything" now calls account/delete, which removes the device's contacts, sessions, alerts, locations, events and encrypted evidence files and revokes its credentials at once. If a real alert is still live, those rows stay until it ends (48 h at most) so contacts keep their link, then the hourly job finishes the deletion. Deletion is best effort from the phone: if the phone is offline, the server copy expires on the retention schedule instead.
  • Sealed date details are encrypted with a server-held key so the contact's browser can show them. A stronger design puts the key in the link's URL fragment so the server can never decrypt them.
  • PIN hashing uses salted SHA-256 inside the Keychain. A 4-digit PIN would be brute-forceable if the Keychain were extracted, so we'll move to a slow KDF or a Secure Enclave–bound check.
  • Prototype accounts: Twilio is on a trial account (US SMS is blocked by A2P 10DLC rules, and calls go only to verified numbers), Noonlight is sandbox-only, and the Noonlight alarm PIN is a fixed placeholder. None of these are production settings.
  • Not yet built: App Attest, Sign in with Apple account recovery, contact opt-in confirmation, and an independent security review. All are needed before any public release.
Our commitment

Before SafetySense goes to real students, we'll have an independent privacy and legal review, publish a plain-language privacy policy, and ask UNM's Information Security & Privacy Office and campus advocates to review the data flows in this document.
